## 확인할 계약

Android Car 주차 신호는 Pleos Vehicle SDK 안전 차단과 별개다. 다음은 공급자 또는 해당 플랫폼의 공개 계약으로 확인해야 한다. 답변을 받기 전 기본값을 추측하지 않는다.

1. `GEAR_SELECTION`이 변하지 않을 때 동기 조회의 timestamp가 무엇을 뜻하며 언제 갱신되는가? 동일 값 재보고와 새 하드웨어 관측을 구분할 방법이 있는가?
2. `PERF_VEHICLE_SPEED`의 연속 보고·정지 중 갱신·조회 캐시 및 timestamp 시간 기준은 해당 Pleos 이미지에서 어떤가? 최대 전달 지연과 불명 상태를 알 수 있는가?
3. 기어·속도·UX 제한은 서로 다른 시점에 읽히는데, 하나의 유효한 주차 상태로 묶을 수 있는 공개 계약이나 원자적 스냅샷이 있는가?
4. 서비스 연결 유실의 통지 순서, 동기 조회와의 경합, 이전 값 폐기 및 재연결 후 새 증거로 인정할 조건은 무엇인가? 유실 직후 화면을 잠그는 보장이나 대체 수단이 있는가?
5. 설치 이미지에서 `getPropertyStatus()`의 가용성과 기존 상태 값 의미는 무엇인가? 공식 대체 API가 있어도 대상 런타임 확인 전 기존 `getStatus()`를 임의 교체하지 않는다.

## Fake에서 먼저 검증할 항목

`ParkingFreshnessModelTest.kt`는 실제 차량 저장소와 SDK를 사용하지 않는 테스트 전용 Fake에 속성 값·상태·속성 timestamp·조회 시작/완료 시각·연결 세대·UX 제한을 각각 주입한다. 가상의 검증된 계약, 활성 연결 감시, 같은 연결 세대에 대해 검증됐다고 가정한 증거도 별도로 주입한다. 이 가정은 실제 플랫폼의 계약·검증 API가 아니다. 가정이 모두 충족될 때만 Fake의 P·정지·UX 허용이 열리며, 없거나 증거가 불명확하면 잠긴다. 기어 timestamp가 지속적으로 갱신된다는 가정은 없다. 이 모델은 운영 앱에 연결되지 않았다.

이전 에이전트 시도는 Gradle 구성 단계의 배포본 JAR 접근 거부로 종료 코드 1이었으며 태스크가 시작되지 않았다. 이후의 사용자 터미널 결과는 위에 기록했다. 기존 사용자 데이터와 APK는 건드리지 않았다.

### 2026-11-08 테스트 범위 코드 대조

- 당시 테스트 모델의 `allows`는 모든 결과에 `false`를 반환했다. 이후 가상의 계약과 감시를 명시적으로 주입했을 때의 허용·재잠금 시험을 추가했지만, 이 가정이 실제 Pleos에서 제공되거나 운영 `FeatureGate`가 위험을 차단한다는 뜻은 아니다. 연결 세대도 테스트 입력일 뿐 실제 어댑터가 보유하는 세대 증거가 아니다.
- 별도 기존 `FeatureGateTest`의 Fake 증거 시험은 `observedAt` 기준 2.5초 경계와 읽기 중단을 모델링한다. 이는 속성 timestamp의 신선도가 아니라 앱에 전달된 폴링 증거의 나이 시험이다. `ParkedApp` 소스에는 200ms 간격의 재평가 트리거와 lifecycle 중단 시 증거 초기화가 있으나, 실제 기기에서 정확한 잠금 지연이나 Compose 화면 제거가 검증됐다는 뜻은 아니다. 스레드 지연·연결 감지 지연의 상한도 확인되지 않았다.
- 다음 구현 이전에 공급자 계약을 확보하고 테스트 전용 모델과 운영 어댑터 사이의 명시적 상태 전달·세대 무효화·관측 가능한 연결 유실을 설계해야 한다. 실신호 정책을 추측하거나 테스트의 항상 차단 결과를 운영 기능의 동작으로 보고하지 않는다.

| 시나리오 | 확인할 결과 |
|---|---|
| 유효한 P·정지·UX 허용 | 확인된 시간 및 연결 계약을 모두 만족할 때만 허용 |
| D단·움직이는 속도·권한 거부·unavailable/error | 잠금; 오류를 P 또는 정지로 대체하지 않음 |
| 오래된 기어·오래된 속도·미래 timestamp·서로 다른 시각 | 확인된 계약으로 신뢰성을 판단할 수 없으면 잠금. 기어 변화 없음만으로 오래됐다고 단정하지 않음 |
| 조회 중 P→D, 순차 조회 중 상태 전환 | 혼합 결과가 안전한 단일 시점의 증거로 취급되지 않음 |
| 조회 완료 직전·직후 연결 유실, 늦은 응답 | 이전 세대의 응답이 다시 허용하지 못하며 유실 감지 지연도 측정 |
| 재연결·동일 값 재보고·고착된 timestamp | 이전 세대의 값은 재사용하지 않고, 재연결 후 신뢰 조건이 충족될 때만 허용 |
| 읽기 지연·시간 역행·UX 제한 미상 | 잠금; 시간 제한이 속성 자체의 신선도 보증과 혼동되지 않음 |

계약이 확정되지 않은 항목을 정상 또는 실패로 미리 단정해 테스트를 작성하지 않는다. 값이 오래 유지된 ONCHANGE 속성에 임의 만료시간을 적용하면 정상 주차도 막을 수 있고, 만료하지 않으면 오래된 값을 허용할 수 있다.

## 별도 기기 검증 전 준비

- 기기 접근이 허용되고 안전한 별도 테스트 환경과 복구 절차가 마련된 경우에만 실행한다. 기존 사용자 데이터와 설치 APK를 보존하고, 상태 변경이 필요하면 시작 상태를 기록하고 복원 가능성을 먼저 확인한다. 복원이 불가능하면 해당 실험을 중단한다.
- 단조 시계 기준의 상대 시간, 속성 상태, 연결 세대, 제한 허용 여부만 필요한 범위로 기록한다. 위치·목적지·차량 식별자·토큰·개인정보는 기록하지 않는다.
- 정지 중 동일 기어 및 속도 재조회, 명시적 상태 전환, 연결 유실과 재연결을 각각 분리해 확인한다. 특정 변화가 timestamp를 갱신하지 않았다는 관찰은 그 기기·조건에서만 유효하며 전체 플랫폼 계약으로 일반화하지 않는다.
- 실제 화면의 잠금·해제와 SDK 결과를 구분해 기록한다. 실차 운행 중 조작으로 검증하지 않으며 실차 안전과 출시 준비는 별도 평가한다.

## 현재 근거

- [Android 차량 속성](https://developer.android.com/reference/android/car/VehiclePropertyIds): 기어는 ONCHANGE, 속도는 CONTINUOUS.
- [CarPropertyValue](https://developer.android.com/reference/android/car/hardware/CarPropertyValue): 속성 시간은 `elapsedRealtimeNanos()` 기준이며 값 사용 전 상태 확인이 필요하다.
- [Car 서비스 생명주기](https://developer.android.com/reference/android/car/Car.CarServiceLifecycleListener): 서비스가 준비되지 않은 동안 접근을 중단한다.
- 자세한 현재 구현·사용자 보고 빌드 결과와 미검증 항목은 `SDK_CALL_AUDIT.md`, `FEATURE_STATUS.md` 참조.
